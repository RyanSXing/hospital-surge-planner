## Remaining release gates

- **Hosted final workflow and performance:** public HTTPS/authentication, an actual OCI worker run and private Object Storage export download with complete checksum verification passed (`evidence/cloud-acceptance.json`). The first hosted seven-screen check passed. The compound browser workflow reached completed scenario and comparison runs plus an update before its overall 180-second harness deadline; the final patch workflow will use a 900-second overall allowance. The original OCI workloads used `planning_baseline` (84 initial patients), 30 days and a sustained 70% arrival increase. The 10-replication run took 51.696 seconds worker wall time, missing the 10-second target; the 100-replication run took 150.08 seconds, missing its 60-second target. Both failures are preserved in the `cloud-benchmark-30d-*-before-optimization.json` files. Host profiling identified repeated trace snapshots and percentile calls. The optimized release `e4c54e2` passed all 108 Python and 28 frontend tests, including complete cached/uncached trace equality and exact aggregation outputs. On the same frozen inputs, that release improved the hosted 30-day runs to 45.237 seconds for 10 replications and 93.523 seconds for 100, still above both targets. A separate eight-child startup diagnostic measured 24.07 seconds with inline inputs versus 3.78 seconds using the same trusted input from one private file; the initializer repair and worker fencing/upload cleanup shipped in release `c4ff451`, which passed all 156 Python and 31 frontend tests. Its authenticated hosted smoke run and fully checksummed export passed. The final short workloads improved to 35.328 seconds for 10 replications and 82.757 seconds for 100; both still miss the 10/60-second targets. Warm bounded reads measured 36–111 ms. The 365-day/100-replication hosted workload completed in 765.138 seconds worker wall time, missing the 600-second target. Annual warm metrics/state/census/events/checkpoint samples measured 47–216 ms; cold metrics and state reads were 7.13 and 12.05 seconds respectively, so those are not warm-response claims (`evidence/cloud-benchmark-365d-100r.json`). A subsequent engine/Replay patch is being verified before the final browser run. The diagnostic is not a simulation acceptance result (`evidence/cloud-pool-startup-diagnostic.json`).
- **Final browser checks:** the full desktop/mobile matrix passed 11 tests, with 7 deliberate mobile skips for computational workflows tested on desktop. Separate recovery tests passed 2/2; candidate-resource and exact replay controls passed 2/2. Fresh desktop/mobile screenshots passed after the final contrast/layout edits (`evidence/browser-screens-patch-final.json`, 2/2 passed after final responsive chart and inspector fixes) and were visually reviewed. Final dedicated browser checks passed 3/3 (`evidence/browser-release-workflows.json`): 51-scenario library and global search pagination, calendar week/month horizons, clone/archive source immutability, ICU-to-clinic rejection followed by an actual bounded ward transfer, and exact patient filters/unit staffing and timeline evidence. The final hosted compound workflow remains to be repeated after the performance window.
- **Long-horizon response budgets:** the local 365-day, 100-replication engine benchmark passed in 409.700 seconds, excluding API/database/artifact work. `evidence/api-year-read-performance.json` separately verifies a 365-day selected trace with 54,339 active patients, a bounded 500-patient state response and exact counts; warm state p95 was 0.007 seconds and cold reconstruction 3.692 seconds. Hosted end-to-end performance remains a separate gate.
- **Concurrent catalog reads:** ten authenticated viewers completed 250 requests with mutation denial enforced. Metrics, state, census and event p95 latency stayed below 500 ms, but the original dataset catalog p95 was 4.214 seconds (`evidence/cloud-ten-viewers.json`). The immutable dataset-card cache repair passed dedicated workspace/database/revision isolation tests; the hosted ten-viewer check must be repeated on the optimized release.
- **One local queue-delay observation:** run `run_cbabe314400e4896b468` waited approximately 300 seconds after creation, then completed in 2.015 seconds. A subsequent fresh run dispatched immediately and completed in 1.795 seconds. The original delay's cause is not established; it must not be described as a confirmed logging or lease defect. Durable queue/lease recovery tests have independent passing evidence.

These are explicit verification gates, not claims that the delivered application lacks the repaired workflows below.
