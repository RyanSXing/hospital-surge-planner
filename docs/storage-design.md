# Durable storage design

PostgreSQL is authoritative. The implementation stores versioned domain records in a `documents` table with a discriminator, workspace ID, optimistic revision, timestamps, and a JSON payload. Each committed dataset contains the complete canonical normalized entity collections; scenarios, immutable scenario revisions, individual replication metadata, updates, comparisons, alert rules, members and settings are separately addressable records. Durable queue/status, sessions, idempotency keys and audit events use dedicated relational tables. SQLite implements the same contract for local tests and development.

This is a deliberate difference from a separate SQL table for every patient, unit, slot and assignment. Snapshot ingestion and immutable replay use the same complete normalized object as the engine, avoiding partial replacement or divergent reconstruction. PostgreSQL transaction boundaries cover dataset commits, scenario freeze plus job enqueue, update application plus child lineage, and comparison jobs. Dataset/scenario input hashes are verified by workers before execution. Private immutable artifact storage holds full inputs, metrics, individual completed replications, selected traces, exports and checksums; Redis is only delivery infrastructure and cannot erase authoritative jobs.

Protection is split between SQL and application validation. SQL enforces row primary keys and the workspace/operation/idempotency-key uniqueness constraint. Conditional revision updates prevent lost draft writes. The API checks referenced record kind and workspace at every boundary, and the complete dataset validator checks internal IDs, references, assignment intervals, resource conservation, placement and coverage before commit. Immutable committed datasets and frozen revisions have no mutation or deletion API. Job inputs are frozen; history remains available after edits and corrections.

JSON-contained references are **not database foreign keys**. There is no PostgreSQL trigger enforcing every patient-to-unit, scenario-to-dataset or job-to-revision relationship, and direct SQL privileges can bypass application immutability. This design therefore requires all ordinary writers to use the API and limits direct database write credentials to trusted migration/operations processes. A future normalized relational projection or reference-edge table could add database-level FK enforcement without changing the immutable snapshot/engine contract. It must not be described as already present. Existing API tests cover invalid internal references, cross-workspace access, frozen inputs, optimistic conflicts, atomic invalid-import rejection and checksum corruption.

Structural request contracts are Pydantic models exposed in OpenAPI. `scripts/generate_api_types.py` derives `apps/web/src/api-contracts.ts`; typed command wrappers in `commands.ts` use these types at browser write boundaries. Domain constraints remain authoritative server-side because they depend on the selected immutable dataset and operational interval.
